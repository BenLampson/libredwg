# R2004 large-file exception: `3F.00.dwg`

## Scope

`3F.00.dwg` is a 175,732,763-byte R2004 file in the project-owned corpus.  It
is intentionally excluded from the normal 20-file blocking-versus-Stream
parity set because the blocking reader materializes an unusually large object
section and can consume excessive memory.  It remains a separate Stream and
large-file regression target.

## Upstream history

- LibreDWG issue #1305 identified the blocking reader's hard-coded
  `0x2f000000` (about 790 MiB) R2004 decompression cap.
- BenLampson's PR #1306 made that cap configurable through
  `LIBREDWG_MAX_DECOMP_SIZE` while preserving the safe default.
- The maintainer discussed removing the cap and checking input positions in
  PR #1307.  PR #1307 was merged, but its final four commits were general fuzz
  guards and did not change the R2004 decompression cap.
- This branch therefore carries the original configurable-cap commit from
  PR #1306.  The default remains unchanged.

## Verified behavior

Measured on 2026-07-12 with the pure C `dwgprobe` Stream path:

| Mode | Result | Objects | Entities | Non-entities | Decode errors | Peak RSS |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Stream object map | `warn 0x40`, usable | 1,769,224 | 1,081,856 | 687,368 | not decoded | 211 MiB |
| Stream decoded objects | `warn 0x40`, usable | 1,769,224 | 1,081,856 | 687,368 | 0 | 366 MiB |

Both Stream runs used the R2004 object-map path with file mapping and did not
fall back to `dwg_read_file`.  Total object-record size was 1,057,880,538 bytes;
the largest record was 64,632,663 bytes.

Without an override, the blocking reader reports:

```text
Invalid section AcDb:AcDbObjects count or max decompression size.
Sections: 35863, Max size: 29696
```

It then continues with zero decoded objects, so its final `SUCCESS` text must
not be treated as a successful open of this file.

With `LIBREDWG_MAX_DECOMP_SIZE=0x7fffffff`, a guarded blocking-reader run
crossed the former hard limit and began decompressing `AcDbObjects`.  The run
was deliberately stopped after 45 seconds before full object materialization;
it showed no hard-cap error and reached about 330 MiB working set.  This proves
the override is active, not that unrestricted blocking decode is memory-safe.

## Operational rule

Use the Stream API for this file.  Do not use unrestricted blocking decode as
an automated regression: historical runs consumed tens of GiB.  If blocking
decode is required for investigation, set `LIBREDWG_MAX_DECOMP_SIZE` explicitly
and enforce an external time and memory limit.
